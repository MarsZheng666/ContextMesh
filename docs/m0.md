# M0：远程 Session 持久化

M0 提供 HTTP 服务、PostgreSQL 存储、DeepSeek Harness 持久化插件和 CLI。支持原生事件保存、读取、正常关闭后的恢复，以及显式确认旧进程已停止后的异常恢复。跨机器主动 Handoff 和模型切换控制器属于 M1/M2，尚未实现。

## 本地启动

使用 Node 24.15.0 或兼容的 Node 24 版本；仓库包含 `.node-version` 与 `.nvmrc`。不要使用之前预研时默认的 Node 22。

```sh
cd /Users/zhengximing/Documents/contextMesh
nvm use
corepack enable
pnpm install --frozen-lockfile
pnpm build
cp .env.example .env
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

将最后生成的值写到 `.env` 的 `CONTEXTMESH_TOKEN`。`.env` 不纳入 Git。服务默认只监听 `127.0.0.1:8787`。

在一个终端启动仅绑定本机的开发数据库，数据保存在 `.contextmesh/postgres`：

```sh
pnpm db:local
```

在另一个终端启动服务；服务会检查持久化配置并按版本初始化数据库：

```sh
pnpm start
```

数据库脚本使用项目安装的 PostgreSQL 二进制，不安装全局服务、不创建系统用户；按 Ctrl-C 停止，数据保留。它仅用于本地开发。生产环境使用独立管理的 PostgreSQL、备份与 TLS。

CLI 自动读取当前目录的 `.env`：

```sh
pnpm cli list
pnpm cli stat SESSION_ID
pnpm cli export SESSION_ID
pnpm cli operation OPERATION_ID
```

export 将完整原生日志写到标准输出；按需重定向至自己管理的文件，避免意外提交会话内容。

## 接入 DeepSeek Harness

已验证的 npm 兼容组合为 DSH `0.2.1-rc.3`、Cordis `4.0.5` 与原生格式 4。上游源码预研固定 commit 与 npm 包不应视为完全相同的构建；兼容性以本次安装并执行测试的包版本为准。

插件位于 `packages/adapter-deepseek`，构建后入口为 `dist/index.js`，带类型声明与安装 bundle。服务启动后，在启动 Harness 的环境中设置 `CONTEXTMESH_TOKEN` 和可选的 `CONTEXTMESH_ENDPOINT`。远端地址要求 HTTPS；本机地址允许 HTTP。

### 使用基于 base 的 profile

构建后，可以通过正常的官方插件安装命令接入已有 web、desktop 或其他 base profile：

```sh
dsh plugin --profile web add file:/Users/zhengximing/Documents/contextMesh/packages/adapter-deepseek
dsh --profile web
```

bundle 停用 `session-persistence-jsonl`，插入 ContextMesh provider，要求 agent-loop 等待 sessionPersistence；保留 base 的 checkpoint policy。安装时会修改指定的 Harness profile，M0 开发测试没有改动用户的真实 profile。

已自动测试官方 base 的配置合成，以及构建插件在官方 SDK profile 中的加载和真实 agent-loop 恢复。桌面/Web 界面交互和用户现有 profile 的个性化配置没有逐一验收；不要将配置合成检查当作完整 GUI 验收。

### sdk-minimal

sdk-minimal 的默认后端行名为 `sessions`，与 base 不同。不要直接套用默认 bundle。`examples/deepseek/sdk-minimal.patch.yml` 展示对应配置；插件模块必须先在该 profile 的依赖解析范围中可解析。自动化测试使用插件构建入口的绝对 file URL，隔离在临时 DSH_HOME 中，不修改真实安装。

官方 SDK 测试通过 initialize、工作目录变更、正常 shutdown，再在新进程调用 session/resume，验证真实 agent-loop 的持久化恢复；不发送模型请求、不使用真实密钥。

## 存储与接口语义

- 完整事件作为 JSON 文本存入 PostgreSQL TEXT，序号单独索引。避免 JSONB 对 NUL 和未配对 Unicode 的限制；HTTP 校验关闭自动类型转换，不修改事件值。
- 同一 namespace 的 native ID 唯一；额外 incarnation 区分删除后重用的空 Session，旧句柄不能读到新实例。
- 同一个 Session 最多一个写者。事务检查写句柄与 epoch；默认租约 60 秒，插件默认每 15 秒续期。
- create 的空 pending Session 只对创建它的插件实例可见。第一次非空 append 或 flush 后公开物化；没有写入或 flush 就 close 时删除。
- 单次远程 append 上限 512 个事件、HTTP 请求体上限 8 MiB。插件拆分较大事件批次，读取按固定结束切点分页。单个超过请求限制的事件会明确失败，不静默截断。
- append 在同步事务提交后响应；flush 排空实时队列并确认持久化进度。service.flush 刷新该实例的全部写句柄并聚合错误。
- header 与事件历史不重写；fork 的 inheritedEventCount 独立保存。未知必需事件在解释或 write-open 时拒绝，未知 ignorable 记录原样保留。
- 所有连接使用同一权威数据库，无滞后读副本。operationId 的事务结果保留在 cm_operations；M0 不自动清理幂等记录和已关闭句柄，需要后续定义保留策略后再做维护工具。

## HTTP API

除 `/health/live` 外均需 `Authorization: Bearer ...`。服务端将凭证映射到配置的单一 namespace。

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| `/health/ready` | GET | 数据库就绪、协议版本、租约时间 |
| `/v1/sessions` | POST / GET | 创建 pending Session / 分页列表 |
| `/v1/sessions/:id` | GET | metadata；不可见或不存在返回 session=null |
| `/v1/sessions/:id/handles` | POST | 打开 read/write 句柄 |
| `/v1/handles/:id/events` | GET | offset、length、end 分页读取 |
| `/v1/handles/:id/append` | POST | 幂等追加连续批次 |
| `/v1/handles/:id/flush` | POST | 持久化屏障与空 Session 物化 |
| `/v1/handles/:id/renew` | POST | 续期当前写权 |
| `/v1/handles/:id/close` | POST | 幂等释放，保留失败关闭状态 |
| `/v1/operations/:id` | GET | 查询已提交操作的结果 |
| `/v1/sessions/:id/recover` | POST | 确认旧执行者已停止后的显式恢复 |

网络超时可能发生在事务提交之后。客户端自动使用相同 operationId 重试；重试耗尽时错误携带 operationId。应查询该操作或保持相同 ID 重试，不生成新 ID 猜测写入未发生。客户端取消也不代表已提交的远端事务回滚。

## 异常恢复

正常关闭会释放写权，可直接通过 Harness 原有恢复入口接续。进程崩溃后，不自动夺取租约：

1. 确认旧 Harness 及它启动的工具都已停止。
2. 等待旧租约到期；仍有效的写权会拒绝强制恢复。
3. 执行下面的显式恢复命令，再使用 Harness 的 Session 恢复入口。

```sh
pnpm cli recover SESSION_ID --confirm-stopped
```

租约与 fencing 只保护日志写入，不能撤销正在执行的外部副作用。数据库重启不会自动释放逻辑写权。日志已确认持久化不等于任意正在执行的工具都可以安全重试。

## 运行检查

```sh
pnpm check
```

检查包括格式、TypeScript、服务与插件构建、官方两组共享契约、HTTP 故障、数据库竞争写权、事务回滚、数据库立即停止后的恢复、独立服务重启及官方 SDK 的真实 agent-loop 恢复。没有 TEST_DATABASE_URL 时自动启动并关闭临时 PostgreSQL；提供该变量可使用专用测试数据库。测试必须使用专用实例，不指向生产库。

共享契约来自固定上游 commit，保留原 MIT 许可和来源记录。两组共 32 个登记案例，其中物理文件 torn-tail 案例在 PostgreSQL 后端不适用，不执行该分支；由事务中途失败和数据库恢复测试验证本后端的原子性。测试夹具仅替换公共包导入并调整一个历史格式的类型断言，没有降低断言要求。

## 部署与当前限制

提供 `Dockerfile` 和 `deploy/compose.yml`；需要设置 POSTGRES_PASSWORD 与 CONTEXTMESH_TOKEN。Compose 默认仅将 HTTP 端口绑定到本机，数据库不暴露宿主端口。非本机部署请在服务前配置 TLS。

```sh
docker compose -f deploy/compose.yml up --build
```

Docker/Compose 和 Linux CI 配置已提供，但本机没有 Docker，未执行容器构建；已执行的本地测试平台为 macOS arm64、Node 24.15.0。真实模型请求、桌面/Web GUI、M1 Handoff 与 M2 模型接力尚未验收。完整的已执行证据见 [M0 验证记录](m0-validation.md)。服务端当前只承诺数据库进程崩溃恢复，不承诺磁盘损坏、数据中心故障或多实例高可用。
