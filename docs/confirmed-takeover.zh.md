# 确认接管后，在 Codex 中自动续跑

[English](confirmed-takeover.md) · [Codex 配置与快照](codex.zh.md) · [服务升级](runtime.zh.md#从-schema-6-或-7-迁移到-8)

用于将未完成的 DSH 任务转移到 Codex CLI。**你在接收端确认后**，ContextMesh 先检查 B，再让 A 安全停止，保存最终历史并转移所有权，随后在 B 启动一次续跑。当前方向为 DSH → Codex，两种 Agent 保留各自的原生历史，不进行无人确认的自动调度。

需要将稳定的 Codex 归档带回新 DSH 会话时，使用[归档返回](codex-return.zh.md)。该独立流程复制上下文，不接管运行中的 Codex 任务。

## 准备接收端

- Server 和参与设备使用同一经审核的 ContextMesh 源码版本。本流程需要数据库结构 **8** 和 `cross-agent-takeover-v1`；已有数据库升级前按停机迁移流程处理。
- 源端 DSH 及唯一的 `dsh-contextmesh-handoff` 插件保持在线，且确认持有有效写者。离线或状态不明的写者需要显式恢复，不能直接抢占。
- 单独安装受支持的 Codex CLI（已验证 **0.154.0**），在 B 配置其登录及模型提供方，通过 `contextmesh setup` 连接服务。B 只需配置自己的模型，不复制 A 的模型凭据。
- 选择 B 已存在的项目根目录。普通目录无需 Git；Git 项目需两端相同基准提交且工作区干净。此 Codex 流程不自动应用文件传输、不克隆仓库，也不搬运未提交改动。
- 支持文本和已确认的历史工具引用，空会话保留在 DSH 中。不支持的附件、不确定的工具效果、超限历史会阻止转移；运行中的终端、任务和后台进程不能迁移。

## 确认并运行

使用已构建的源码目录时，将下文 `contextmesh` 换成 `pnpm cli`：

```sh
contextmesh list
contextmesh codex takeover SOURCE_SESSION_ID \
  --cwd /absolute/path/to/project-root \
  --model YOUR_LOCAL_CODEX_MODEL \
  --workspace-write --confirm
```

`--confirm` 授权本次接管，并将所需历史发送到 B 配置的模型提供方。执行前核对模型、提供方配置、目录和文件权限。Codex 默认只读；`--workspace-write` 明确允许编辑工作区，来源使用工作区写权限时必须选择。暂不支持来源的完全访问权限。A 的绝对路径和模型不会覆盖 B 的选择，已有项目映射会复用，不静默改写。

保持这个前台命令运行。进度及操作编号、交接编号写入 stderr；最终 JSON 返回交接记录、新的 `codex:` 会话编号和已确认的续跑结果。可用 `--operation UUID` 固定接收操作身份，重复使用不会重新执行任务。`--state-dir`、`--codex-home`、`--codex-bin` 与 [Codex 指南](codex.zh.md)一致。

1. **预检 B。** 检查本地目录和原生权限策略，再在临时只读线程中携带可迁移历史，进行一次受限模型就绪调用。此检查禁用命令、补丁、已连接应用、配置的 MCP、钩子和协作能力，可能产生模型用量，但不执行原任务。模型、配置或历史不兼容时，A 继续运行。
2. **准备 A。** 检查当前上下文和项目映射，冻结新输入与新工具准入，等待已派发工具执行体结束，再次检查工作区并授权源端停止。停止授权前准备失败，A 保持运行；工具等待超时不能被视为工具已取消。
3. **停止并保存 A。** 取消未完成的模型轮次，flush 最终事件并关闭原生写者。不能确认关闭时禁止转移。若任务在取消前自然完成，不创建续跑。
4. **转移所有权。** 把最终历史导入独立的原生 Codex 线程，远程归档准备状态，再原子关联源、目标。A 保留只读历史并显示 Codex 会话编号，不再申请原会话的写者。
5. **续跑一次。** 在 `turn/start` 前持久化一次性执行声明。历史工具调用作为引用文本传入，不作为可执行调用重放。B 的终态结果归档后才确认执行。后续指令使用 `contextmesh codex run CODEX_SESSION_ID --message "..."`。

同一设备的配对凭据可用于独立的 DSH、Codex 端点，不会争用设备进程身份；撤销设备会同时撤销两者。同一 Server 命名空间内的授权设备仍属于同一信任范围。

## 如何理解结果

所有权状态 `completed` 仅表示已经转移到关联的 Codex 会话。另行查看 `executionState`：

| 执行状态      | 含义                                                               |
| ------------- | ------------------------------------------------------------------ |
| `none`        | 来源空闲或自然完成，Codex 没有启动任务。                           |
| `pending`     | 所有权已转移，续跑尚未领取。                                       |
| `dispatching` | 已保存一次执行声明，尚未确认原生结果。                             |
| `completed`   | 本次原生续跑轮次结束并已归档；模型仍可能说明缺少信息或有后续工作。 |
| `failed`      | 原生轮次失败或被中断，先核对结果再给新指令。                       |
| `uncertain`   | 可能已经执行，请勿重发，先核对已有原生历史。                       |

## 查看与恢复

```sh
contextmesh codex takeover-status HANDOFF_ID
# 也可用此接收端私有日志中的操作编号查看状态。
contextmesh codex status CODEX_SESSION_ID
```

使用相同的私有状态目录和原生 Codex 主目录。本地日志与绑定是恢复资料，不能代替 Server 持久化的历史。接收端若在所有权转移前退出，先检查源端和交接记录，核实旧执行及工具停止，再走[源端交接恢复](handoff.zh.md)。原生创建或注入回执丢失时需要核对，不能盲目再建一次导入。显式恢复前来源保持保留状态。

所有权转移后，先停止并核实旧 Codex 进程**及其工具**均已结束，再执行：

```sh
contextmesh codex takeover-recover HANDOFF_ID --confirm-stopped
```

尚未领取的 `pending` 续跑会先核对并恢复已停止的写者，绑定到重启后的接收进程，再消费首次执行声明。`dispatching` 或 `uncertain` 只归档已经结束的原生结果，核对客户端消息与轮次编号，**不再启动轮次**。仍在执行的后台工作、缺失的原生历史，或已领取但没有匹配终态证据的任务，会保持阻塞并要求人工核对。不猜测任务没有执行，不撤销外部工具副作用，也不把租约过期视为进程退出。

源端关闭不明，或停止后导入未完成时，所有权保持冻结待核对。所有权转移成功但 Codex 运行失败时，DSH 来源仍只读，不静默回退已完成的所有权转移。核对不确定操作后，按恢复状态处理，不新建另一次接管。

## 验证范围

测试使用真实 DSH 和 Codex CLI 进程、独立临时主目录、临时 PostgreSQL 及本地脚本化 Responses 提供方，覆盖未完成与空闲任务、预检期间自然完成、工具执行边界、模型及工作区预检失败、并发领取、丢失回执和接收端重启不重放。这验证原生生命周期与连续性，不代表付费线上模型推理质量或真实多机部署已验收。
